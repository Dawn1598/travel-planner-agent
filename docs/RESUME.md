# 简历项目描述

## 可直接使用的版本

**行间——基于 Agent 与 RAG 的智能旅行规划系统**

**技术栈：** Python、Django、LangChain、DeepSeek、MCP、RAG、FastEmbed、SQLite、Playwright

**项目介绍：** 面向个性化旅行规划场景，结合用户出发地点、旅行日期和偏好，通过 Agent 动态调用地图与攻略检索工具，生成包含景点、交通、餐饮和住宿的可交互行程。

**项目职责：**

- **Agent 工具编排：** 基于 LangChain 实现“工具选择—执行—结果反馈”的 ReAct 式循环，接入高德 MCP 查询地点、路线及沿途酒店餐馆，支持按需补问与反馈修订。
- **时间分层 RAG：** 使用 Playwright 采集攻略正文与发布时间，通过中文 BGE 模型完成分块向量化；按近期到历史逐层检索，结合相关性与充分性检查，在证据不足时触发补采和重新检索。
- **确定性时间校验：** 将行程建模为可通过工具增删改查的时间表，使用 Python 校验活动重叠、交通间隔与日期范围；冲突反馈给 Agent 修订，最终活动直接从校验后的时间表生成。
- **Web 与工程实现：** 基于 Django 实现表单、会话持久化、后台任务及进度展示，提供可选脱敏调试日志；完成 44 项自动化测试，并配置 Nginx、Gunicorn、Supervisor 部署方案。

## 篇幅较短时使用

**行间智能旅行规划系统｜Django / LangChain / MCP / RAG**

- 基于 LangChain 实现 ReAct 式旅行规划 Agent，结合高德 MCP 的路线、酒店和餐馆查询与小红书攻略检索，支持多轮补问和行程修订。
- 构建按发布时间逐层扩展的本地 RAG，通过中文 BGE 向量检索、证据充分性判断和按需补采完成资料获取与复用。
- 设计程序管理的时间表工具，校验时间冲突、交通间隔与旅行日期范围；实现 Django 网页交互、草稿持久化及调试日志，44 项自动化测试通过。

## 面试时可以展开的设计

**为什么用 Agent？**

旅行需求不固定，信息缺口也不同。模型根据上一轮工具结果决定继续查路线、查资料、编辑时间表还是询问用户，减少固定流水线中不必要的查询。

**RAG 为什么还要调用模型？**

数据库检索、时间过滤、相似度计算由程序完成。模型只检查召回片段是否真正回答查询，允许多篇资料补充，并明确缺少的信息。

**如何优先使用新资料？**

先按发布时间过滤，再计算相似度；近期资料不足才扩大时间窗口。未知发布时间独立标记，不用采集时间冒充发布时间。新发布不等于事实一定有效，因此仍需检查内容是否适用。

**为什么单独做时间表？**

模型适合选择活动和解释安排，时间重叠、交通间隔、日期范围属于确定性计算。把这些校验放在程序中，可以返回具体冲突让 Agent 修改，也避免最终文字行程绕过工具中的时间表。

**高德和小红书各解决什么？**

高德用于地点定位、路线和周边查询；小红书用于游览方式、体验等非结构化攻略。酒店实时价格、空房不属于已保证的能力。

## 描述边界

- 这里的 ReAct 指工具调用与观察反馈循环，不是自行训练模型，也不是 LangGraph 工作流。
- 向量保存在 SQLite，查询使用 NumPy 相似度计算；没有实现专用向量数据库、分布式检索或大规模 ANN。
- 时间表冲突检查通过不等于路线和现实情况绝对可行，交通耗时仍依赖外部查询与模型填入的数据。
- 44 项测试是程序测试数量；没有做正式的规划准确率、响应速度提升或用户规模统计，不填写未经验证的百分比和业务数据。
- 当前时间校验、RAG、工具循环、后台线程池和部署配置均有代码；分布式任务队列、预订支付、图片 OCR 不属于已实现功能。

简历中的项目时间、角色和个人职责应按实际参与情况填写；面试前建议重点阅读 `agent.py`、`knowledge.py` 和 `schedule.py`，能解释每条职责对应的实现。
